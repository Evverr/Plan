# PlanX: правила для ИИ-помощников

Этот файл читают все, кто пишет код в PlanX: Codex, Claude в облаке, Claude Code в VS Code и Qwen Code (через `QWEN.md`).
Истории разговоров друг друга мы не видим, поэтому важные решения записываем сюда.

## Кто есть кто

- **Женя (Zheka, GitHub `Evverr`)** — владелец проекта. Ставит задачи, пробует результат руками и решает, что сливать в `main`. Не разработчик: пиши по-русски, коротко, что нажать и что ввести, а не как устроен git.
- **Codex** — делает задачи в своих ветках `codex/<коротко-о-задаче>` и открывает PR в `main`.
- **Claude (облако)** — проверяет PR: смотрит изменения, запускает проверки, пишет замечания в PR. Свои большие задачи делает в ветках `claude/...`.
- **ВижуалКлод (Claude Code в VS Code у Жени)** — мелкие правки внешнего вида прямо в `main` на Маке.

## Как работаем

1. Перед началом работы возьми свежий `main`.
2. Одна задача — одна ветка — один PR в `main`. В `main` напрямую не пушь (это делает только Женя через ВижуалКлода).
3. Перед PR прогони проверки по размеру задачи (ниже). В описании PR по-русски: что сделано и как это попробовать руками.
4. Замечания из ревью исправляй новыми коммитами в той же ветке, историю не переписывай.
5. Сливает PR только Женя.
6. Vercel сам собирает превью каждого PR и пишет ссылку в комментарии: по ней Женя пробует результат.

**Если проект открыт без git** (папка из архива, нет `.git`): веток и PR нет. Работай прямо в файлах, в конце коротко перечисли, какие файлы изменены и зачем: Женя перенесёт их в `main` через ВижуалКлода.

Сообщения коммитов — по-английски, одной строкой о том, что изменилось для пользователя. Перед коммитом посмотри `git diff` и добавляй только файлы своей задачи, по именам (`git add <файлы>`, не `git add -A`). Файл `.mcp.json` не коммить никогда.

## Проверки

Объём проверок зависит от размера задачи. Не трать время на лишнее: Женя ждёт результат.

**Мелкая правка** — цвет, текст, отступ, подсказка, правка в одном файле стилей или README. Полные проверки не нужны. Если менялся `.ts`/`.tsx`, хватит `npm run typecheck`; если только `.css` или текст, можно ничего не запускать. Женя сразу смотрит результат на localhost.

**Средняя и крупная задача** — новая функция, логика, несколько файлов, всё в `src/model`, `src/collab`, `server/`. Прогони всё:

```bash
npm test           # vitest
npm run typecheck
npm run build
```

Есть и проверки в браузере (e2e, `tests/e2e/checks/*.mjs`, около 300 штук, идут ~10 минут): `npm run e2e` — все, `npm run e2e -- <часть имени>` — только подходящие, например `npm run e2e -- labs`. После правки логики гоняй только тот файл e2e, который она задевает; все e2e — один раз перед пушем, вместе с тремя командами выше. Два прогона e2e одновременно не запускай. Временные проверки клади в `tests/e2e/checks/zz-tmp.mjs` и удаляй после.

Все проверки должны проходить. Тесты не отключай и не пропускай, чтобы получить зелёный результат. Полные проверки нужны и перед слиянием любого PR Кодекса, кроме мелких правок по описанию выше.

**Работа ВижуалКлода в `main`.** Мелкие правки коммить локально без проверок. Пуш — это веха: перед ним один раз прогони полные проверки (`npm test`, `npm run typecheck`, `npm run build`, `npm run e2e`) и почини, если что-то сломалось. Пушь только когда Женя просит («пуш»), например перед тем как дать задачу Кодексу или облачному Claude (они видят только запушенное) и в конце рабочего дня.

`npm install` нужен только если менялся `package.json` или папки `node_modules` ещё нет.

## Экономия времени и токенов

У Жени ограниченный тариф, каждое лишнее действие стоит денег.

- Читай только файлы, нужные для задачи. Не обходи весь проект «для контекста»: структура есть в `README.md`.
- Мелкую правку делай сразу, без плана, браузера и e2e-тестов.
- Отвечай коротко: что сделано и что нажать. Без пересказа кода и длинных объяснений.
- Не переспрашивай, если задачу можно понять однозначно. Если легко понять не так, спроси одним коротким вопросом (подробнее — «Как понимать просьбы Жени» ниже).
- Не запускай одну и ту же проверку повторно, если код с тех пор не менялся.

## Как понимать просьбы Жени

- **«А можем…?», «а если…?», «скажи…» — это обсуждение, а не задание.** Ответь: можно ли, сколько это стоит, что советуешь — и спроси «Делать?». Код меняй только после явного «делай», «давай», «сделай так».
- **Описание поведения в настоящем времени — обычно просьба.** «Если выбрали ячейку, то панель исчезает» значит «сделай, чтобы исчезала». Если нет слов «сейчас», «баг», «почему-то», «заметил» — это просьба; если непонятно, спроси одним вопросом: «Это просьба так сделать или сейчас так происходит?».
- **Не подменяй элемент похожим.** Женя может назвать деталь неточно («плюсик», а имел в виду крестик), но место он называет точно. Если в названном месте нет ровно такого элемента, спроси, что из того, что там есть, он имел в виду; не правь похожую деталь в другой функции.
- **Предупреждай о большой переделке.** Если просьба звучит мелко, а потребует переделать много (много файлов, новые библиотеки, заметный рост размера), сначала скажи это с цифрами и предложи вариант дешевле. Женя не может сам оценить цену идеи.
- **Не отменяй правило молча.** Если просьба ломает правило, заданное намеренно (так написано в комментарии в коде или так договорились раньше), назови это правило и предложи узкий вариант, который его не ломает.
- **Кнопки и меню его программ называй по-английски**, как на экране (у Жени английский интерфейс в Claude и других программах), сам текст ответа — по-русски. Это не касается PlanX: его интерфейс на русском.

## Проект

Доска для планирования в духе Miro, весь интерфейс на русском. Подробности и структура папок — в `README.md`.

- TypeScript + React, отрисовка доски на `<canvas>`.
- Данные доски в Yjs (CRDT), отдельно от отрисовки: `src/model`. Каждый элемент — свой `Y.Map`.
- Совместная работа с самого начала: свой сервер синхронизации (`server/`), офлайн-кэш в IndexedDB, курсоры участников (`src/collab`). Любое изменение данных должно корректно сливаться у нескольких людей сразу.
- Стартовая страница «Мои доски» с полками и папками: `src/shelf`. Шаблоны: `src/shelf/templates.ts`.
- Продакшен: https://plan-x-ten.vercel.app (только сайт, без сервера синхронизации).
- Тест совместной работы: https://plan-78i6.onrender.com (Render, бесплатный тариф, Dockerfile: сайт и сервер вместе; засыпает через 15 минут, диск не сохраняется). Совместная работа и коннектор работают только здесь: у Vercel нет сервера. Оба сами собирают `main` после пуша.
- Коннектор для Claude (MCP): `server/mcp.ts`, адрес `/mcp/<MCP_KEY>`. Без переменной `MCP_KEY` выключен. Ключ лежит только в настройках Render и у Жени, в репозиторий его не пиши.

## Правила, о которых легко забыть

- **Новые функции — пробные.** Новая функция кладётся в `src/labs` и получает переключатель в окне «Настройки» из меню доски, раздел «Нововведения» (список `LABS` в `src/labs/labs.ts`, проверка `labOn(id)`). Так Женя пробует её и решает, оставить или убрать. Убрать = удалить её файл и строчки с `labOn`. Новый переключатель по умолчанию включён (исключения — список `START_OFF` там же). В подсказке переключателя (`hint`) опиши простыми словами, что функция делает, и обновляй её, когда функция меняется.
- **Всплывающие окна появляются одинаково.** Любое новое меню, панель, подсказка или окно появляется общей анимацией: прозрачность 0→1 и сдвиг на `--slide` (5,33 px) с той стороны, откуда оно выходит. Дай ему класс `.pop` или добавь его в список в `src/styles/moves.css` («How every popup comes in») и в `POPUPS` в `src/ui/leaving.ts` (так оно и исчезает). Свою анимацию появления не делай.
- **Панель, которую сменяет другая для того же объекта, перетекает в неё** (`morphPanel` / `morphFrom` в `src/labs/textButton.ts`: оболочка меняет ширину, кнопки плавно сменяются), а не уезжает, чтобы приехала другая.
- **Подсказка внизу экрана** — событие `planx:toast` с `{ text, bottom: true }`; кнопка в ней — `action` (надпись) и `run` (что делает). В текстах для пользователя пиши официально и понятно, без внутренних словечек вроде «шарики».
- **Округляй.** Если Женя просит изменить число в разы или на проценты, бери ближайшее круглое (15% вдвое меньше → 8%, а не 7,5%) и назови его в ответе.
- **У Жени Mac, файловая система не различает регистр.** Никогда не делай два файла, имена которых отличаются только регистром (например, `Labs.tsx` рядом с `labs.ts` ломает сборку).
- **Иконки** — свои SVG 24×24 в `assets/icons`, только заливка, без обводок. После изменений: `npm run icons` (пересобирает `src/icons/icons.json`). Цвет `#333333` становится цветом иконки. Полный набор от Жени (868 обычных и столько же `-solid`, с теми же именами) лежит в `assets/icon-set`: это запас, в окно «Иконки» он не попадает. Нужную иконку копируй оттуда: в `assets/icons` для окна «Иконки», в `src/ui/panel-icons` для панелей.
- Пиши код в стиле окружающего: те же имена, та же плотность комментариев.
- Не добавляй зависимости без нужды; версии в `package.json` точные.
- В сообщения коммитов и описания PR не добавляй подписи вроде `Co-Authored-By: …` и «Generated with …»: только сам текст.

## Проверка работы Кодекса

Порядок для ВижуалКлода, когда Женя просит «проверь PR Кодекса»:

1. Сделай `git fetch` и найди самую свежую ветку `codex/...`, которая ещё не слита в `main` (или PR с номером, который назвал Женя).
2. Расскажи Жене простыми словами, что в ней изменилось.
3. Проверь, что изменения соответствуют правилам из этого файла, и прогони проверки по размеру задачи (раздел «Проверки»).
4. Если есть проблемы, не исправляй их сам: напиши Жене списком, чтобы передать их Кодексу.
5. Если всё в порядке, переключись на эту ветку, чтобы Женя посмотрел результат на localhost.
6. После «ок» от Жени слей ветку в `main` (через `gh pr merge`, а если `gh` нет — `git merge` и `git push`), вернись на `main` и сделай `git pull`.
